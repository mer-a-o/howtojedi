# About `ingest` suites

 In `suite_config.py` multiple configuration can be listed. For example in [`r2d2_ingest` suite](https://github.com/GEOS-ESM/swell/blob/develop/src/swell/suites/r2d2_ingest/suite_config.py):

 ```
 src/swell/suites/r2d2_ingest/           ← the suite (one flow.cylc)
├── flow.cylc
└── suite_config.py
    ├── r2d2_ingest                     ← base config, others inherit from it
    ├── ingest_obs_marine               ← specific config for marine obs
    ├── ingest_obs_cf                   ← specific config for CF obs
    └── ingest_background_cf            ← specifc config for CF background (jdi collection)
```


In this example, `ingest_obs_cf` and `ingest_background_cf` are not separate suites. They are two configurations of `r2d2_ingest`, and they select different "branches" of the same `flow.cylc` via flags (`download_convert_pipeline`, `ingest_background_pipeline`). 


Here's an example of what is in a **experiment directory**:

```
<experiment_root>/<experiment_id>/
├── configuration/
│   └── jedi/
│       └── interfaces/
│           └── geos_cf/
│               ├── download_observations/    ← where to get raw granules
│               ├── convert_observations/     ← how to run the IODA converter
│               ├── ingest_observations/      ← what to store in R2D2
│               ├── observations/             ← JEDI obs-space YAML templates
│               └── model/
└── <experiment_id>-suite/
    ├── flow.cylc
    ├── experiment.yaml    ← the rendered answers
    └── modules            ← source this to run tasks by hand
```


## What is R2D2?

**R2D2** (Research Repository for Data and Diagnostics) is a **data catalogue**. Swell asks
it "give me the TEMPO NO₂ file for this window" and R2D2 answers with a file.


R2D2 is a **metadata database plus a storage location**. The server holds a database of what exists and where. When you request to fetch a file/item , the client asks the server *where*, then transfers the file from storage. With R2D2, users don't need to know about the file's name or location.  They need to use R2D2 keys to describe the file so R2D2 can fetch the file.


Swell's own [R2D2 introduction](https://geos-esm.github.io/swell/#/examples/r2d2_intro)
has the full architecture diagram and the store/fetch reference. Read it. What follows is a high-level summary tailoed for CF application.

### Items

Everything in R2D2 is an *item*, and the item type determines which keys identify it. If
the keys are incorrect and you get a 400 from the API. Here is a list of R2D2 items:

| Item | Identified by these keys | Used in CF by |
|------|---------------|---------------|
| `observation` | `provider`, `observation_type`, `file_extension`, `window_start`, `window_length` | `IngestObs`, `GetObservations` |
| `forecast` | `model`, `experiment`, `resolution`, `step`, `date`, `file_extension` | `SaveBackground`, `GetBackground` |
| `feedback` | `experiment`, ... | `SaveObsDiags` |
| `bias_correction` | `model`, `experiment`, `provider`, `observation_type`, `file_type`, `date` | not used for CF |

Notice the asymmetry as each item requires different identification keys:

**Observations have no `experiment`.** They are shared input data and independent of the experiment. Once `tempo_no2_tropo`
for a given window is in R2D2, *every experiment* fetches the same file. This is the whole point of
the ingest suites — ingest once, use forever...

**Forecasts and feedback do have an `experiment`.** The reason being, the results may vary based on the experiment configuration so we need to distinguish between the output files. 

#### Provider (for observation)

`provider` is R2D2's answer to "who made this observation file". For now we also use this key to save different versions of a retrieval. For example `nasa_v03` or `nasa_v04` for TEMPO observaion. The default values are set in 
`src/swell/configuration/jedi/observation_ioda_names.yaml` but can be overwriten with `suite_config.py` or in `override.yaml`:

```yaml
  - ioda name: tempo_no2_tropo
    full name: TEMPO tropospheric column NO2
    inst type: retrieval
    provider :  nasa_v03
```

More about override and experiment configuration in the next lecture.

#### Model names

Swell's model component names and R2D2's model names are not the same, and there's a
translation table in `src/swell/utilities/r2d2.py`:

```python
R2D2_MODEL_MAP = {
    'geos_atmosphere': ['geos'],
    'geos_marine':     ['mom6', 'cice6'],
    'geos_cf':         ['geos_cf'],
}
```

For CF they happen to coincide (`geos_cf` → `geos_cf`), so you can mostly ignore this —
but know the table exists, because when you see `-m geos_cf` on a command line that is the
*Swell* name.

#### Experiment lifetime

When an experiment is registered in R2D2 it gets a lifetime, and **everything stored under
it inherits that lifetime**:

| Lifetime | Retention | Use for |
|----------|-----------|---------|
| `debug` | days/weeks | testing |
| `science` | months | research |
| `publication` | years | published results |
| `release` | permanent | operational / reference |




# Running `ingest_obs_cf` suite

The `ingest_obs_cf` suite gets raw observations into R2D2 so that downstream suites (like
[`hofx_cf`](3.hofx_cf.md)) can fetch them. For GEOS-CF composition observations it runs the full
**download → convert → ingest** pipeline: it downloads raw obs files from a remote server, converts
them to IODA format with the ioda-converters, and stores the IODA files in R2D2.

`ingest_obs_cf` is not a standalone suite directory — it is one of several suite variants defined
inside the shared **`r2d2_ingest`** suite in
[`src/swell/suites/r2d2_ingest/`](https://github.com/GEOS-ESM/swell/tree/develop/src/swell/suites/r2d2_ingest).
The variants (`r2d2_ingest`, `ingest_obs_marine`, `ingest_obs_cf`, `ingest_background_cf`) share the
same [`flow.cylc`](https://github.com/GEOS-ESM/swell/blob/develop/src/swell/suites/r2d2_ingest/flow.cylc)
but differ in the defaults set in
[`suite_config.py`](https://github.com/GEOS-ESM/swell/blob/develop/src/swell/suites/r2d2_ingest/suite_config.py).
Which branch of the graph runs is controlled by two switches:

- `download_convert_pipeline` — when `True`, run download + convert + ingest (this is what
  `ingest_obs_cf` sets).
- `ingest_background_pipeline` — when `True`, run the background-saving branch instead (used by
  `ingest_background_cf`).

When both are `False` (e.g. `ingest_obs_marine`), only `IngestObs` runs — the raw files are assumed
to already be staged.

## Running the suite

The steps are the same as any other suite (see [3.hofx_cf.md](3.hofx_cf.md)):

1. Load the SWELL environment.

2. Create the experiment by running `swell create ingest_obs_cf`.
This will print the launch command, e.g.:

```bash
SwellCreateExperiment:  
SwellCreateExperiment: Experiment successfully installed. To launch experiment use: 
SwellCreateExperiment:  
SwellCreateExperiment:   swell launch /discover/nobackup/mabdiosk/SwellExperiments/swell-ingest_obs_cf/swell-ingest_obs_cf-suite
SwellCreateExperiment:  
```

3. Launch it with `swell launch <path_to_experiment.yaml>` using the path from the previous step.

Use `cylc scan` to find the active experiment name and `cylc tui <experiment_name>` to watch the
tasks run.

### Defaults worth knowing

The `ingest_obs_cf` block in `suite_config.py` ships with these notable defaults:

- `model_components: ['geos_cf']` — a single model component, so each cycle task is instantiated as
  `<Task>-geos_cf`.
- `download_convert_pipeline: True` — enables the full download/convert/ingest branch.
- `jedi_build_method: use_existing` — a JEDI build is linked (needed for `pyioda`/converters).
- `obs_to_download` / `obs_to_ingest: ['tempo_no2_tropo']` — the observation type(s) handled.
- `converter_path` — path to the directory containing the ioda-converter scripts.
- `dry_run: False` — actually download/convert/store (set `True` to just log what *would* happen).
- `store_as_symlink: False` — store real copies in R2D2 rather than symlinks.

As always, customize these with an override file rather than editing source — see
[2.configure.md](2.configure.md).

## Tasks in `ingest_obs_cf` suite

With `download_convert_pipeline: True`, the suite runs these tasks:

- CloneJedi
- BuildJediByLinking
- BuildJedi
- DownloadObs
- ConvertObsToIoda
- IngestObs

### Dependencies (`=>`) in this suite

The one-time `R1` block clones and builds JEDI, with the same linking-then-fallback logic as
`hofx_cf`:

```
CloneJedi => BuildJediByLinking?
BuildJediByLinking:fail? => BuildJedi
```

(`?` = optional output, `:fail?` = failure trigger — see [3.hofx_cf.md](3.hofx_cf.md) for the full
operator rundown.)

The per-cycle block chains the pipeline:

```
DownloadObs-geos_cf => ConvertObsToIoda-geos_cf
BuildJediByLinking[^]? | BuildJedi[^] => ConvertObsToIoda-geos_cf
ConvertObsToIoda-geos_cf => IngestObs-geos_cf
```

So for each cycle: download the raw files, and — once a JEDI build is available (`[^]` = the initial
build instance, `|` = OR so either build path suffices) — convert them to IODA, then ingest the IODA
files into R2D2.

### What each task does

- **CloneJedi** — Clones the JEDI source (or links an existing source) via `jedi_bundle`, based on
  `jedi_build_method`.
- **BuildJediByLinking** — Links to a pre-existing JEDI build directory (the fast path, used here
  since `jedi_build_method: use_existing`). The converters run out of this build.
- **BuildJedi** — Fallback that compiles JEDI from source if linking fails.
- **DownloadObs** — For each obs in `obs_to_download`, reads
  `download_observations/<obs_name>.yaml` and fetches the raw files from a remote server via `https`
  (scraping a directory listing, auth via `~/.netrc`) or the NASA `cmr` API. Raw files land in
  `<cycle_dir>/download/<obs_name>/`.
- **ConvertObsToIoda** — For each obs, reads `convert_observations/<obs_name>.yaml`, gathers the raw
  files from `<cycle_dir>/download/<obs_name>/`, and runs the ioda-converter script (from
  `converter_path`, defaulting to `<experiment>/jedi_bundle/build/bin`). The IODA output is written
  to `<cycle_dir>/ioda/<obs_name>/<output_filename>`.
- **IngestObs** — Reads per-observation metadata from
  `configuration/jedi/interfaces/<model>/ingest_observations/<obs_name>.yaml`, resolves the file
  path for the cycle, and stores the file in R2D2 as an `observation` item (keyed by experiment,
  observation type, and DA window).

All of `DownloadObs`, `ConvertObsToIoda`, and `IngestObs` honor `dry_run: true`, in which case they
log what they *would* do without touching the network or R2D2.

## Exploring log and run directories

Same layout as other suites (see [3.hofx_cf.md](3.hofx_cf.md)):

- **Run directory** — per cycle/model under
  `<experiment_root>/<experiment_id>/run/<YYYYMMDDTHHMMSSZ>/<model_component>/`. For this pipeline
  that includes `download/<obs_name>/` (raw files) and `ioda/<obs_name>/` (converted IODA files).
- **Log directory** — cylc job logs under
  `~/cylc-run/<experiment_name>/log/job/<cycle_point>/<task_name>/<submit_num>/` with `job.out` and
  `job.err`. This is the first place to look when `DownloadObs` (network) or `ConvertObsToIoda`
  (converter) fails.

## What are the final outputs

The deliverable is **IODA-format observation files registered in R2D2**. `IngestObs` calls
`r2d2.store(item='observation', observation_type=<obs_name>, ...)` for the current cycle's window, so
after a successful run the observations are available in R2D2 for any suite (e.g. `hofx_cf`'s
`GetObservations`) to `r2d2.fetch` by experiment id, observation type, and window.

Set `store_as_symlink: true` to register symlinks to the IODA files rather than copying them into
the datastore, and `dry_run: true` to validate the pipeline end-to-end without writing anything to
R2D2.
