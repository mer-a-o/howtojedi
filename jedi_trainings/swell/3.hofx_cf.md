# Running `hofx_cf` suite

The `hofx_cf` suite runs the JEDI H(x) (observation operator) application for the GEOS-CF
(composition forecast) interface. It clones/links a JEDI build, fetches a background and
observations for each cycle, renders the JEDI YAML, runs the `hofx` executable, and produces
observation-space feedback files plus EVA diagnostics.

To run the default `hofx_cf` suite (without any additional input) follow these steps:

1. Load the SWELL environment.

2. Create the experiment by running `swell create hofx_cf`.
This will print out:

```bash
SwellCreateExperiment:  
SwellCreateExperiment: Experiment successfully installed. To launch experiment use: 
SwellCreateExperiment:  
SwellCreateExperiment:   swell launch /discover/nobackup/mabdiosk/SwellExperiments/swell-hofx_cf/swell-hofx_cf-suite
SwellCreateExperiment:  
```

3. Launch your experiment by running `swell launch <path_to_experiment.yaml>`. You can find this path in the output log of the previous step.

`cylc scan` will show the name of the active cylc experiment.
You can view the active experiment by running `cylc tui <experiment_name>`.

With cylc tui you can watch the tasks as they get queued and executed in real time.

## Tasks in `hofx_cf` suite

All the tasks and their dependencies are defined in [`src/swell/suites/hofx_cf/flow.cylc`](https://github.com/GEOS-ESM/swell/blob/develop/src/swell/suites/hofx_cf/flow.cylc). Let's take a closer look.

Here's the list of the tasks in `hofx_cf`:

- CloneJedi
- BuildJediByLinking
- BuildJedi
- GetBackground
- GetObservations
- StageJediCycle
- RenderJediObservations
- RunJediHofxExecutable
- EvaObservations
- SaveObsDiags
- CleanCycle

### Defining dependencies in cylc with `=>`

Cylc builds a task graph from the `[scheduling][[graph]]` section. The `=>` operator means
"depends on" — the task on the left must succeed before the task on the right can start. So

```
GetObservations-{{model_component}} => RenderJediObservations-{{model_component}}
```

reads "run `GetObservations` first, and only once it succeeds run `RenderJediObservations`."
A few other bits of syntax show up in this suite:

- `?` marks an *optional* output, so the graph doesn't stall if that task/branch doesn't run
  (e.g. `BuildJediByLinking?`).
- `:fail?` triggers off a *failure* — `BuildJediByLinking:fail? => BuildJedi` says "if linking
  to an existing build fails, fall back to building from source."
- `|` is a logical OR — `BuildJediByLinking[^]? | BuildJedi[^] => RunJediHofxExecutable` means
  the executable can start once *either* build path has completed.
- `[^]` refers to the first cycle point, i.e. the initial (`R1`) instance of a task. This is how
  the one-time build tasks feed every cycle.

The graph is split into two blocks: an `R1` block for tasks that run once (clone and build JEDI),
and a per-cycle block (looped over `cycle_times` and `model_components` with Jinja2) for the
tasks that run every cycle. Since `hofx_cf` uses a single model component (`geos_cf`), each
cycle-dependent task is instantiated as `<Task>-geos_cf`.

### What each task does

- **CloneJedi** — Clones the JEDI source (via `jedi_bundle`) or links to an existing source
  directory, depending on the `jedi_build_method` in the experiment dictionary.
- **BuildJediByLinking** — Links to a pre-existing JEDI *build* directory (fast path). It aborts
  if `jedi_build_method` isn't `use_existing`/`use_pinned_existing`, which is what lets the graph
  fall back to `BuildJedi`.
- **BuildJedi** — Compiles JEDI from source with `jedi_bundle` when no suitable existing build can
  be linked. This runs on a compute node with its own SLURM directives.
- **GetBackground** — Uses R2D2 to fetch the background (first-guess) fields for the cycle.
- **GetObservations** — Uses R2D2 to fetch the observation files for the cycle. If an obs file is
  missing it can fall back to an empty obs file so the run continues.
- **StageJediCycle** — Stages the static/cycle-dependent files JEDI needs (from
  `configuration/jedi/interfaces/<model>/stage.yaml`), resolving resolution and processor keys.
- **RenderJediObservations** — Renders the per-observation JEDI YAML (obs spaces, window
  parameters, CRTM coefficients, etc.) into the cycle directory.
- **RunJediHofxExecutable** — Assembles the full `hofx` YAML and runs the JEDI `hofx` executable.
  This is the main compute task and runs on a compute node with SLURM directives.
- **EvaObservations** — Runs EVA (Evaluation and Verification of the Analysis) on the
  observation-space output to produce diagnostic plots/statistics.
- **SaveObsDiags** — Stores the observation feedback (diag) files back to R2D2. Only added to the
  graph when R2D2 is enabled (i.e. not `--skip-r2d2`).
- **CleanCycle** — Removes large intermediate files from the cycle directory based on the
  `clean_patterns` list, after EVA and (if applicable) the R2D2 save have completed.

## Exploring log and run directories

Everything for a given experiment lives under the experiment directory, i.e.
`<experiment_root>/<experiment_id>` (for the example above,
`/discover/nobackup/mabdiosk/SwellExperiments/swell-hofx_cf`).

**Run directory.** Each task that receives a cycle and model writes into a per-cycle directory:

```
<experiment_root>/<experiment_id>/run/<YYYYMMDDTHHMMSSZ>/<model_component>/
```

for example `.../swell-hofx_cf/run/20211212T000000Z/geos_cf/`. This is where the fetched
background and observation files, the rendered JEDI YAML, the `hofx` executable output, the
feedback files, and the EVA output are written. (`CleanCycle` later prunes the large files here.)

**Log directory.** Cylc keeps its own run/log tree under `~/cylc-run/<experiment_name>/`. The
per-task stdout/stderr for every job live under:

```
~/cylc-run/<experiment_name>/log/job/<cycle_point>/<task_name>/<submit_num>/
```

with `job.out` (stdout, including the swell task logging) and `job.err` (stderr) for each task
instance. This is the first place to look when a task turns red in `cylc tui`.

## What are the final outputs

The key deliverables of `hofx_cf` are the **observation-space feedback files** (the H(x) diag
files) produced by `RunJediHofxExecutable`, together with the EVA diagnostics generated by
`EvaObservations`.

Locally, the feedback files are written into the cycle's run directory (see above) before
`CleanCycle` runs. For durable storage, `SaveObsDiags` registers them in **R2D2** as `feedback`
items, keyed by the experiment id, observation type, and data-assimilation window
(`window_start`/`window_length`). This step is skipped when the experiment is created with
`-k/--skip-r2d2`.

### Fetching feedback files later

Because the feedback files are stored in R2D2, you can retrieve them after the run (or from a
different experiment) with the `r2d2` utility — the same interface `GetObservations`/`GetBackground`
use to `r2d2.fetch(...)` items. Fetch the `feedback` item for the matching experiment id,
observation type, and window to pull the diag files back to a local path.
