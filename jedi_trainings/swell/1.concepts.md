## What is SWELL?

SWELL is a workflow layer that manages **tasks** such as creating the run directory for each assimilation window, copying or linking relevant observations, backgrounds, or any other input files in the run directory, building JEDI input YAML files, running JEDI executble, and handling JEDI or model output files.

SWELL uses Cylc to determine the depencies between different tasks. The order of different **tasks** is usually defined in a file called `flow.cylc`. 


### Tasks

SWELL tasks are Python classes that live under [`src/swell/tasks`](https://github.com/GEOS-ESM/swell/tree/develop/src/swell/tasks). 

| Task | Does |
|------|------|
| `CloneJedi` | Clone the JEDI source repos |
| `BuildJediByLinking` | Try to symlink an existing build (fast path) |
| `BuildJedi` | Compile JEDI (slow path, only if linking failed) |
| `GetBackground` | `r2d2.fetch` the forecast files this cycle needs |
| `GetObservations` | `r2d2.fetch` the obs files|
| `RenderJediObservations` | Fill in the obs-space YAML templates |
| `StageJedi` | Put static files (coefficients, geometry) in place |
| `RunJediHofxExecutable` | Actually run JEDI under SLURM |
| `EvaObservations` | Generate diagnostic plots and stats |
| `SaveObsDiags` | `r2d2.store` the feedback files |
| `CleanCycle` | Delete the large intermediates |

You can run any of them by hand:

```bash
swell task GetObservations $config -d $datetime -m geos_cf
```

### Suites, suite configs, experiments

A **Suite** directory lives under [`src/swell/suites/`](https://github.com/GEOS-ESM/swell/tree/develop/src/swell/suites). In this folder you will find a `flow.cylc` (the task depency graph), `suite_config.py` (list of suite configuraitons), and EVA folder (holds EVA YAMLs for plotting).

 In `suite_config.py` multiple configuration can be listed. For example in [`r2d2_ingest` suite](https://github.com/GEOS-ESM/swell/blob/develop/src/swell/suites/r2d2_ingest/suite_config.py):

 ```
 src/swell/suites/r2d2_ingest/           ← the suite (one flow.cylc)
├── flow.cylc
└── suite_config.py
    ├── r2d2_ingest                     ← base config, others inherit from it
    ├── ingest_obs_marine               ← specific config for marine obs
    ├── ingest_obs_cf                   ← specific config for CF obs
    └── ingest_background_cf            ← specifc config for CF background (jdi collection)
```


In this example, `ingest_obs_cf` and `ingest_background_cf` are not separate suites. They are two configurations of `r2d2_ingest`, and they select different "branches" of the same `flow.cylc` via flags (`download_convert_pipeline`, `ingest_background_pipeline`). 

An **experiment** is what `swell create` command produces which is a directory on disk with a rendered `experiment.yaml`, a copy of the configuration tree, and a Cylc suite ready to launch. 

You can create an `ingest_obs_cf` experiment by running:

```bash
swell create ingest_obs_cf
```

Running `swell create` withouth additional word will print out all the available suites.

Here's an example of what is in a **experiment directory**:

```
<experiment_root>/<experiment_id>/
├── configuration/
│   └── jedi/
│       └── interfaces/
│           └── geos_cf/
│               ├── download_observations/    ← where to get raw granules
│               ├── convert_observations/     ← how to run the IODA converter
│               ├── ingest_observations/      ← what to store in R2D2
│               ├── observations/             ← JEDI obs-space YAML templates
│               └── model/
├── jedi_bundle/
└── <experiment_id>-suite/
    ├── flow.cylc
    ├── experiment.yaml    ← the rendered answers
    └── modules            ← source this to run tasks by hand
```

Note that if you want to make changes in any of the files under `configuration` directory after running `swell create` you need to change the files under `<experiment_root>/<experiment_id>/configuration/` and not under SWELL source code. 


## What is R2D2?

**R2D2** (Research Repository for Data and Diagnostics) is a **data catalogue**. Swell asks
it "give me the TEMPO NO₂ file for this window" and R2D2 answers with a file.


R2D2 is a **metadata database plus a storage location**. The server holds a database of what exists and where. When you fetch, the client asks the server *where*, then transfers the file from storage.

Swell's own [R2D2 introduction](https://geos-esm.github.io/swell/#/examples/r2d2_intro)
has the full architecture diagram and the store/fetch reference. Read it. What follows is
only what you need for CF.

### Items

Everything in R2D2 is an *item*, and the item type determines which keys identify it. If
the keys wrong and you get a 400 from the API.

| Item | Identified by | Used in CF by |
|------|---------------|---------------|
| `observation` | `provider`, `observation_type`, `file_extension`, `window_start`, `window_length` | `IngestObs`, `GetObservations` |
| `forecast` | `model`, `experiment`, `resolution`, `step`, `date`, `file_extension` | `SaveBackground`, `GetBackground` |
| `feedback` | `experiment`, ... | `SaveObsDiags` |
| `bias_correction` | `model`, `experiment`, `provider`, `observation_type`, `file_type`, `date` | not used for CF |

Notice the asymmetry, because it explains a lot of the CF design:

**Observations have no `experiment`.** They are shared input data. Once `tempo_no2_tropo`
for a given window is in R2D2, *everyone* fetches the same file. This is the whole point of
the ingest suites — ingest once, use forever.

**Forecasts and feedback do have an `experiment`.** The reason being, the results may vary based on the experiment configuration so we need to distinguish between the output files. 

### Provider (for observation)

`provider` is R2D2's answer to "who made this observation file". For now we also use this key to save different versions of a retrieval. For example `nasa_v03` or `nasa_v04` for TEMPO observaion. Swell looks it up from
`src/swell/configuration/jedi/observation_ioda_names.yaml`:

```yaml
  - ioda name: tempo_no2_tropo
    full name: TEMPO tropospheric column NO2
    inst type: retrieval
    provider :  nasa_v03
```

If an observation is missing from this
file, you get `No provider found for observation X` and ingestion fails. Adding a new
observation to the CF system **always** starts here.


### Model names

Swell's model component names and R2D2's model names are not the same, and there's a
translation table in `src/swell/utilities/r2d2.py`:

```python
R2D2_MODEL_MAP = {
    'geos_atmosphere': ['geos'],
    'geos_marine':     ['mom6', 'cice6'],
    'geos_cf':         ['geos_cf'],
}
```

For CF they happen to coincide (`geos_cf` → `geos_cf`), so you can mostly ignore this —
but know the table exists, because when you see `-m geos_cf` on a command line that is the
*Swell* name.

### Experiment lifetime

When an experiment is registered in R2D2 it gets a lifetime, and **everything stored under
it inherits that lifetime**:

| Lifetime | Retention | Use for |
|----------|-----------|---------|
| `debug` | days/weeks | testing |
| `science` | months | research |
| `publication` | years | published results |
| `release` | permanent | operational / reference |

For a monitoring system that is expected to keep running, `debug` is the wrong answer and
you will find out at the worst possible time. Decide this deliberately.

`swell create` registers the experiment in R2D2 automatically and writes the resulting ID
into `experiment.yaml`.
