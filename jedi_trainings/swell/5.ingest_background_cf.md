# Running the `ingest_background_cf` configuration


Background ingest is a simpler worfklow because the JEDI-ready GEOS-CF files already exist on the CSS shared
filesystem. The `ingest_background_cf` configuration registers those background files in R2D2 so that downstream
suites such as [`hofx_cf`](3.hofx_cf.md) can retrieve them with `GetBackground`. The source files
already exist on the CSS shared filesystem, so this workflow does not download, convert, or modify
them. It finds each hourly file and stores its metadata in R2D2, normally using a symlink rather
than making another copy.

Like [`ingest_obs_cf`](4.ingest_obs_cf.md), `ingest_background_cf` is a configuration of the shared
[`r2d2_ingest`](https://github.com/GEOS-ESM/swell/tree/develop/src/swell/suites/r2d2_ingest)
suite rather than a separate suite directory. It sets `ingest_background_pipeline: true`, which
selects the `SaveBackground` branch in the shared
[`flow.cylc`](https://github.com/GEOS-ESM/swell/blob/develop/src/swell/suites/r2d2_ingest/flow.cylc).

## What the suite ingests

GEOS-CF produces one 09Z forecast initialization per day for this collection. The suite treats the
Cylc cycle point as that forecast initialization and registers 24 one-hour steps:

| R2D2 step | Valid time for a 2025-10-02 09Z cycle |
|-----------|----------------------------------------|
| `PT0H` | 2025-10-02 09Z |
| `PT1H` | 2025-10-02 10Z |
| ... | ... |
| `PT15H` | 2025-10-03 00Z |
| `PT23H` | 2025-10-03 08Z |

The cycle must therefore be at 09Z. `SaveBackground` checks this and aborts with an explanatory
message if it receives any other cycle hour.

## Configuring and running the workflow

Start with a dry run. This checks which source files exist and prints the R2D2 operations that
would be performed without storing anything:

```bash
swell create ingest_background_cf
swell launch <path_printed_by_swell_create>
```

Use `cylc scan` to find the active workflow and `cylc tui <workflow_name>` to monitor it. The
default suite configuration processes one cycle, `2025-10-02T09:00:00Z`, with `dry_run: true`.

For a reproducible real ingest, create an override file such as `override_background.yaml`:

```yaml
start_cycle_point: '2025-10-02T09:00:00Z'
final_cycle_point: '2025-10-04T09:00:00Z'
cycle_times:
  - T09

models:
  geos_cf:
    dry_run: false
    background_experiment: geos_cf_oper
    horizontal_resolution: c360
    store_as_symlink: true
    background_source_path: >-
      /css/gmao/geos-cf/NRTv2/priv/ana/Y%Y/M%m/D%d/GEOS.cf.ana.jdi_inst_1hr_glo_C360x360x6_v72.%Y%m%d_%H%Mz.R0.nc4
```

Then create and launch the experiment:

```bash
swell create ingest_background_cf -o override_background.yaml
swell launch <path_printed_by_swell_create>
```

The important settings are:

| Setting | Meaning |
|---------|---------|
| `start_cycle_point` | First 09Z forecast initialization to ingest |
| `final_cycle_point` | Last 09Z forecast initialization to ingest |
| `cycle_times` | Must remain `['T09']` for the current `SaveBackground` implementation |
| `background_source_path` | Python `strftime` template used to locate each valid-time file |
| `background_experiment` | Experiment key under which the forecasts are stored in R2D2 |
| `horizontal_resolution` | R2D2 resolution key; `c360` for the configured NRT collection |
| `store_as_symlink` | `true` registers symlinks; `false` asks R2D2 to copy the files |
| `dry_run` | `true` validates and logs; `false` performs the R2D2 stores |

> **Check the generated configuration:** `SaveBackground` contains code-level fallbacks of
> `geos_cf_v2`, `c360`, and `true`, but a fallback is used only when a key is absent. On the current
> `develop` source, the shared GEOS-CF model defaults can populate `background_experiment` with
> `swell_test` and `horizontal_resolution` with `c90` first. For the configured NRT C360 files,
> explicitly set the intended R2D2 experiment and `horizontal_resolution: c360`, as in the override
> above, and confirm those values in the generated `experiment.yaml` before launching a real
> ingest.

### How the source-path template works

For every step, `SaveBackground` adds the step offset to the 09Z initialization and applies
`datetime.strftime()` to `background_source_path`. For example, at `PT15H`, the valid time has
crossed midnight, so:

```text
Y%Y/M%m/D%d/        -> Y2025/M10/D03/
%Y%m%d_%H%Mz        -> 20251003_0000z
```

This valid-time expansion is why the directory changes automatically when the 24-hour sequence
crosses into the next UTC day.

## Task graph

For this suite, the relevant branch in `flow.cylc` reduces to one task per configured cycle and
model component:

```text
T09: SaveBackground-geos_cf
```

There are no dependencies because the background files are already present on the shared
filesystem. In particular, this branch does not run `CloneJedi`, `BuildJedi`, `DownloadObs`,
`ConvertObsToIoda`, or `IngestObs`.

The runtime entry executes:

```bash
swell task SaveBackground "$config" -d "$datetime" -m geos_cf
```

The task has a 30-minute Cylc execution limit.

## What `SaveBackground` does

The implementation lives in
[`src/swell/tasks/save_background.py`](https://github.com/GEOS-ESM/swell/blob/develop/src/swell/tasks/save_background.py).
For each cycle it:

1. Loads the user's R2D2 credentials.
2. Verifies that the forecast initialization hour is 09Z.
3. Loops from hour offset 0 through 23.
4. Calculates the valid time and R2D2 step (`PT0H` through `PT23H`).
5. Expands `background_source_path` for that valid time.
6. Checks that the source file exists. Missing files generate warnings and are skipped.
7. In dry-run mode, logs what would be stored. Otherwise, calls `r2d2.store()`.
8. Reports the numbers of stored and skipped files.

Each real store uses these R2D2 keys:

```python
r2d2.store(
    item='forecast',
    model='geos_cf',
    experiment=background_experiment,
    resolution=horizontal_resolution,
    date=forecast_start,
    step='PT0H',  # changes for each hourly file
    file_type='bkg',
    file_extension='nc4',
    source_file=source_file,
    store_as_symlink=store_as_symlink,
)
```

Notice that the R2D2 `date` represents the 09Z **forecast initialization**, while `step` locates
the hourly valid time within that forecast.

## `background_experiment` versus `r2d2_experiment_id`

`SaveBackground` stores files under `background_experiment`; it does **not** use the workflow's
`r2d2_experiment_id`. For example, with:

```yaml
experiment_id: swell-ingest_background_cf
r2d2_experiment_id: swell-ingest_background_cf-a1b2c3d4
models:
  geos_cf:
    background_experiment: geos_cf_oper
```

the local workflow is named `swell-ingest_background_cf`, but the background files are indexed in
R2D2 under `geos_cf_oper`. A downstream `hofx_cf` experiment must use the same value:

```yaml
models:
  geos_cf:
    background_experiment: geos_cf_oper
    horizontal_resolution: c360
```

`GetBackground` then fetches `item='forecast'`, `model='geos_cf'`, `file_type='bkg'`, and the
matching experiment, resolution, initialization date, and step.

For example, a 3D `hofx_cf` cycle at 18Z with `window_length: PT6H` computes a 09Z forecast
initialization and requests `PT9H`. That key selects the file valid at 18Z from the 24-file set
registered by the 09Z ingest cycle.

## Logs, files, and troubleshooting

Cylc job output is stored under:

```text
~/cylc-run/<workflow_name>/log/job/<cycle_point>/SaveBackground-geos_cf/<submit_num>/
```

Check `job.out` for each resolved source filename and the final stored/skipped counts, and check
`job.err` for failures. The task base creates the usual local cycle directory under
`<experiment_root>/<experiment_id>/run/<cycle>/geos_cf/`, but `SaveBackground` reads directly from
the configured shared path and does not stage the background files there.

Common problems are:

- **The task aborts immediately:** the cycle hour is not 09Z. Keep `cycle_times: ['T09']` and use
  09Z start/final cycle points.
- **Files are skipped:** compare the expanded path in `job.out` with the CSS directory. A dry run
  still checks `os.path.exists()`, so it reports only source files that are actually present.
- **A downstream suite cannot fetch the files:** make sure `background_experiment`,
  `horizontal_resolution`, model, file type, initialization time, and step match the stored keys.
- **A symlink store reports a permission warning:** the task contains a workaround for an R2D2
  `chmod` issue. It continues only after verifying that the created symlink points to the expected
  source; any other `PermissionError` is raised normally.

## Final output and the handoff to HofX

A successful non-dry run registers up to 24 R2D2 `forecast` items per 09Z cycle. With
`store_as_symlink: true`, the R2D2 datastore contains links to the authoritative CSS files rather
than duplicate NetCDF files. These registered backgrounds are then ready for `hofx_cf` and other
GEOS-CF workflows to retrieve through `GetBackground`.

Together, the two ingest configurations satisfy the input side of the HofX workflow contract:

```text
ingest_obs_cf        → R2D2 observation → GetObservations ─┐
                                                        ├─► RunJediHofxExecutable
ingest_background_cf → R2D2 forecast    → GetBackground   ─┘
```

The producer and consumer configurations must agree on the relevant R2D2 keys. For observations,
that includes the provider, observation type, file extension, and window. For backgrounds, it
includes the model, background experiment, resolution, initialization date, step, file type, and
file extension. Once those contracts match, the HofX configuration does not need to know the
physical source paths used by either ingest workflow.


#### Experiment lifetime for experiment-scoped products

When an **experiment** is registered in R2D2, it gets a lifetime, and products stored under that
experiment inherit its lifetime. This applies to experiment-scoped products such as forecasts and
feedback; observations are shared items and are not identified by an experiment key.

| Lifetime | Retention | Use for |
|----------|-----------|---------|
| `debug` | days/weeks | testing |
| `science` | months | research |
| `publication` | years | published results |
| `release` | permanent | operational / reference |
